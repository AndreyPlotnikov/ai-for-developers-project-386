# Шаг 2. Каркас приложения

Источник: [Hexlet — шаг 2](https://ru.hexlet.io/projects/386/members/54450?step=2). Дата сохранения: 1 ноября 2026 года.

На этом шаге мы собираем каркас: бекенд, фронтенд, программу запуска тестов, линтеры и прогон проверок в GitHub Actions. Функциональности здесь пока нет, появляется рабочая основа, на которую дальше кладутся фичи.

Главный ориентир шага это официальный getting started вашего фреймворка. Открывайте документацию и идите по ней, а команды может выполнять агент. Причина такая: модель помнит прошлые версии инструментов и уверенно предлагает устаревший способ создать проект, подключить сборку или программу запуска тестов. Документация фреймворка показывает актуальный способ, и каркас, собранный по ней, потом не приходится разбирать.

Стек вы выбираете сами. Рекомендуем TypeScript и Vite, для интерфейса shadcn/ui или Mantine: с ними агенты дают более точные подсказки, а типы упрощают правки по ходу проекта. Это рекомендация, вы можете взять свои инструменты. До выбора стека проверьте цепочку TypeSpec, OpenAPI и генератор SDK для языка фронтенда. Клиентский SDK обязателен. Для бекенда генерация типов, схем проверки запросов и маршрутов зависит от фреймворка. Если подходящего серверного генератора нет, реализуйте сервер по контракту и проверьте совпадение тестами.

Тестов на функциональность здесь ещё нет, поэтому в CI достаточно одного дымового теста: приложение поднимается и отвечает. Задача шага в том, чтобы прогон тестов и линтера работал автоматически до появления первой фичи.

Программа запуска тестов находит тесты, выполняет их и сообщает результат. Для JavaScript и TypeScript это может быть Vitest, для Python pytest, для Java JUnit с задачей сборщика. GitHub Actions запускает выбранную вами команду на машине CI. В этом шаге достаточно одного дымового теста, который проверяет запуск приложения и успешный ответ на запрос. Проверки полного сценария бронирования появятся вместе с функциональностью.

Рекомендуем использовать mise для всего окружения разработки. В `mise.toml` фиксируются версии инструментов, переменные окружения, задачи установки, запуска, сборки и проверок. Хуки mise позволяют запускать задачи при установке инструментов или входе в проект. Git-хуки рекомендуем настроить через hk, установленный с помощью mise, и вызывать из них те же проверки. Фоновые серверы и сервисы разработки описываются через daemons mise, чтобы агент мог запускать, останавливать их и смотреть состояние. Для daemons включите `experimental = true` в разделе `[settings]` и зафиксируйте версию pitchfork, который управляет процессами.

Соберите проверки в одну задачу, например `mise run check`. Сейчас она запускает линтер, проверку типов, если она есть в стеке, и дымовой тест. GitHub Actions вызывает эту же команду. По мере разработки в неё добавляются остальные тесты. Выбор другого инструмента допустим, команды и версии должны быть воспроизводимыми.

При выборе инструментов используйте [dev-guardrails](https://github.com/mokevnin/dev-guardrails). В подборке для каждой задачи названы рекомендуемый инструмент, причины выбора и ограничения. Начните с инструментов для своего стека, Git-хуков и CI. Подключайте их к общей команде проверок.

Сразу договоритесь о формате Conventional Commits (`feat:`, `fix:` и так далее) и запишите правило в `AGENTS.md`. Автоматические релизы через release-please подключим на шаге реализации после первой функции. На этапе каркаса их настраивать не нужно.

В конце шага запустите в агенте команду инициализации (`/init` в OpenCode и Claude Code). Агент изучит собранный каркас и предложит `AGENTS.md`: файл с рабочими правилами проекта, который попадает в контекст в начале каждой сессии. Порядок именно такой: на пустом репозитории инициализации нечего изучать, а после каркаса в проекте уже есть команды запуска, тестов и линтера, и они попадают в файл.

Полученный `AGENTS.md` стоит сократить. Агент почти всегда пишет туда лишнее, а рабочий файл короткий: команды, устройство проекта и правила, которые из кода не читаются.

## Требования

- Бекенд и фронтенд запускаются локально.
- В проекте есть команды запуска тестов и линтера.
- Одна команда запускает все текущие проверки локально и в GitHub Actions на каждый push, прогон зелёный. Версии инструментов зафиксированы в проекте.
- Коммиты идут по Conventional Commits.
- В корне репозитория есть `AGENTS.md` с командами запуска, тестов и линтера и с правилом про формат коммитов.
- `AGENTS.md` короткий и без противоречивых правил. В нём только команды, устройство проекта и правила, которые из кода не читаются.

## Ссылки

- [dev-guardrails](https://github.com/mokevnin/dev-guardrails) помогает выбрать инструменты проверок под задачи проекта.
- [mise](https://mise.jdx.dev/) управляет инструментами, окружением и задачами проекта.
- [Хуки mise](https://mise.jdx.dev/hooks.html) запускают команды по событиям окружения.
- [Daemons mise](https://mise.jdx.dev/daemons.html) управляют фоновыми процессами разработки.
- [AGENTS.md](https://agents.md/): формат файла с рабочими правилами проекта для агентов.
- [Vite](https://vite.dev/): dev-сервер и сборка фронтенда.
- [shadcn/ui](https://ui.shadcn.com/): набор UI-компонентов с гибкой настройкой.
- [Mantine](https://mantine.dev/): готовая UI-библиотека для быстрого старта.
- [shadcn MCP Server](https://ui.shadcn.com/docs/mcp): MCP-сервер, через который агент работает с компонентами shadcn/ui.
- [Conventional Commits](https://conventionalcommits.org/): спецификация формата сообщений коммитов.

## Задачи

1. Выберите стек и создайте каркас бекенда по getting started вашего фреймворка.
2. Подключите фронтенд и убедитесь, что он собирается и открывается.
3. Выберите программу запуска тестов под свой стек, подключите её и напишите один дымовой тест запуска приложения.
4. Подключите линтеры.
5. Соберите проверки в одну команду и настройте её вызов из GitHub Actions на каждый push. Рекомендуем mise для версий, задач, хуков и фоновых процессов. Подберите инструменты по dev-guardrails и проверьте их запуск.
6. Запустите инициализацию агента (`/init`), получите `AGENTS.md`, сократите его до рабочего минимума и запишите правило про формат коммитов.

## Результат шага

Каркас приложения запускается локально, одна команда прогоняет проверки на вашей машине и в GitHub Actions, в репозитории есть `AGENTS.md` с рабочими командами.

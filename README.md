# Календарь звонков


[![hexlet-check](https://github.com/AndreyPlotnikov/ai-for-developers-project-386/actions/workflows/hexlet-check.yml/badge.svg)](https://github.com/AndreyPlotnikov/ai-for-developers-project-386/actions)

Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Сценарий

Путь от создания типа встречи до появления записи у владельца.

Владелец:

1. Открывает список типов встреч и создаёт новый: название, описание, длительность (например, «Консультация», 30 минут).
2. Новый тип сразу доступен гостям по своей ссылке. Свободное время считается по рабочим часам владельца в его часовом поясе.

Гость:

3. Без регистрации открывает страницу владельца и выбирает тип встречи.
4. Видит календарь с ближайшими днями и выбирает дату. Справа появляются свободные слоты, длина слота равна длительности типа встречи.
5. Выбирает слот. Время, уже занятое любой встречей, в списке не показывается.
6. Вводит имя и email и подтверждает запись.
7. Видит страницу подтверждения: что, когда, с кем.

Владелец:

8. Открывает список предстоящих встреч и видит новую запись (тип, дата, время, гость) среди встреч всех типов.
9. Этот слот пропадает из свободных у всех типов встреч, в том числе у других типов с пересекающимся временем.

## Обязательные функции

- Владелец один и задан заранее.
- Владелец создаёт типы встреч: название, описание, длительность.
- Владелец видит список предстоящих встреч всех типов.
- Гость без регистрации выбирает тип встречи и видит календарь на 14 дней вперёд.
- Гость бронирует свободный слот, длительность слота равна длительности типа встречи.

## Ограничения

- Нет авторизации, личных кабинетов, интеграций с внешними календарями и уведомлений.
- Окно записи 14 календарных дней, сдвигается со временем.
- Одно время нельзя занять дважды, даже разными типами встреч, включая частичное пересечение. Встреча может начинаться в момент окончания предыдущей.
- Правило о пересечениях действует и для одновременных запросов.
- Приложение собирается в Docker-образ и запускается в контейнере.
- Данные можно хранить в памяти процесса. Тогда перезапуск сбрасывает записи, и это нужно указать в README.

## Требования к API

- Контракт описывается на TypeSpec.
- Из контракта генерируется OpenAPI-спецификация.
- Клиентский SDK для фронтенда генерируется из OpenAPI. Генератор должен существовать для языка фронтенда.
- Серверные типы и маршруты генерируются, если фреймворк это поддерживает. Иначе бекенд реализуется по контракту и проверяется тестами.

## Стек

- Бекенд: TypeScript 6.0.3, Node.js 26.13.0, Hono 4.13.16.
- Контракт: TypeSpec 1.17.0 → OpenAPI 3.0.0 → Orval 8.46.0 → маршруты, типы и Zod-валидаторы Hono.
- Фронтенд: React 19.3.1, TypeScript 7.0.2, Vite 8.3.5, Mantine 9.7.5.
- Пакетный менеджер: pnpm 10.11.0. Зависимости и lockfile находятся отдельно в `backend/` и `frontend/`.

## Установка

Установите [mise](https://mise.jdx.dev/getting-started.html). Версии Node.js, pnpm, hk и pitchfork зафиксированы в `mise.toml`. На Intel macOS для сборки hk и pitchfork дополнительно нужны Rust и Cargo.

```bash
git clone https://github.com/AndreyPlotnikov/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise install
mise run setup
```

`setup` устанавливает зависимости по lockfile и Git-хук pre-commit. Для установки только зависимостей используйте `mise run install`. Запускайте команды через `mise exec --`, если mise не активирован в оболочке.

## Проверки

```bash
mise run check
```

Команда проверяет линтер и форматирование обоих приложений, типы и тесты бекенда, а также сборку фронтенда. Она же запускается в pre-commit и в GitHub Actions на каждый push и pull request.

Фоновые серверы можно запустить и остановить через mise:

```bash
mise daemons start
mise daemons status
mise daemons logs
mise daemons stop
```

## Использование

Сейчас реализован каркас приложения с техническим endpoint `/health`.

```bash
pnpm --dir backend dev
```

В другом терминале запустите фронтенд и откройте адрес, показанный Vite (обычно http://localhost:5173):

```bash
pnpm --dir frontend dev
```

Страница показывает состояние соединения с бекендом. Vite перенаправляет `/health` на `127.0.0.1:3000`. Проверка API из терминала:

```bash
curl --fail http://127.0.0.1:3000/health
# {"status":"ok"}
```

Сборка и запуск собранного приложения:

```bash
pnpm --dir backend build
pnpm --dir backend start
```

`dev` и `build` сначала генерируют OpenAPI и сервер из TypeSpec. После изменения контракта перезапустите `dev` или выполните генерацию в другом терминале:

```bash
pnpm --dir backend generate
pnpm --dir backend typecheck
```

Переменные окружения: `HOST` (по умолчанию `127.0.0.1`) и `PORT` (по умолчанию `3000`). Пример: `PORT=3001 pnpm --dir backend start`.

Сборка фронтенда и отдельная генерация SDK (для обеих команд нужны установленные зависимости бекенда):

```bash
pnpm --dir frontend build
pnpm --dir frontend generate
```

Генерация сначала обновляет OpenAPI из TypeSpec, затем Orval создаёт клиент в `frontend/src/generated/`. Сгенерированные файлы не редактируются вручную. Dev-прокси предназначен для локальной разработки; для опубликованной сборки потребуется настроить маршрутизацию `/health` к бекенду.

[Устройство бекенда и правила генерации](backend/README.md).
